## 1. 文档目的

本文档把整合包中的规则、接口、迁移、测试和校准资料转换成可直接实施的工程方案。

后续开发者和开发代理应先阅读本文，再按具体任务读取被引用的权威文件。本文负责：

- 冻结当前工程架构和依赖方向；
- 明确权威源、生成物和运行时数据的边界；
- 定义领域对象、状态、证据、置信度和发布门控；
- 规定数据编译、Schema、API、持久化和测试策略；
- 给出分阶段产物、退出条件、风险和 Definition of Done；
- 防止把自然语言规则、未验证规则或历史测试结果误当成生产能力。

本文不复制全部规则正文。规则含义仍以原始权威文件为准；本文只规定它们如何被治理、编译、执行和验收。

规范用语：

- “必须”表示合并或发布的硬性门槛；
- “应”表示默认方案，改变时需要 ADR；
- “可以”表示不影响核心契约的实现选择；
- “不得”表示安全、字段权威或数据完整性禁区。

| 关注点 | 权威源 | 使用方式 |
|---|---|---|

| 字段所有权 | 字段权威矩阵 | 下游只读，不得重算 |

需要区分：

- **语义编写真源**决定一条规则原本表达什么；
- **集成契约**决定 Integration V1.0 包含哪些记录、字段和版本；
- **编译生成物**决定某个应用版本实际能执行哪些规则；
- **用户现实资料**决定具体关系证据和安全事实。

任何两层不一致时，构建必须停止并产生 ImportConflict；不得静默回退到另一个文件。

## 4. 产品范围与硬边界

### 4.1 三种主要运行模式

| 模式 | 输入 | 可以输出 | 发布上限 |
|---|---|---|---|
| single_chart_structure | 一份出生资料 | 完整 M0 原局结构 | 不评价具体对象 |
| single_chart_relationship_profile | 一份出生资料 | M1—M4 结构候选、M5 长期需要和观察标准 | 当前实现上限为 FG1 |
| specific_partner_with_reality_data | 命主资料、现实行为、事件和 RG，可选对象命盘 | 具体对象、交换、边界、修复、节奏、RG、AF、FG | 由现实证据和安全门决定 |

two_chart_supplementary 只能增加双方结构背景，不能替代行为、同意、边界、交换、修复和现实目标。

### 4.2 禁止输出

M0—M5 不得直接输出：

- 唯一正缘；
- 必然结婚、必然长久或必然分手；
- 具体婚期、相遇月份、分手日期或大运流年事件；
- 伴侣职业、收入、外貌、生肖或道德定性；
- 医学诊断和用药建议；
- 因适配等级而要求用户进入、继续、原谅或复合；
- 把 FG 表述为成功概率；
- 把 AF 表述为命定结局。

具体时点请求必须返回 E_DYNAMIC_MODEL_REQUIRED。出生日期到四柱的历法和节气换算属于输入标准化，不属于 D0。

### 4.3 安全硬门

以下现实事件具有否决权：

- 暴力或威胁；
- 强迫、跟踪、监控；
- 经济控制；
- 身体或性边界侵犯；
- 撤回同意后仍继续；
- 基本选择权、退出权或退出资源被剥夺。

命中安全停止时必须同时满足：

~~~text
safety_status = safety_stop
report_status = stop
fit_grade = FG0
final_fit_state = AF09
~~~

普通互补、修复、适配及“保护因素抵消风险”的叙事必须停止。安全规则不能进入平均分或加权抵消。

## 5. 架构决策

### 5.1 模块化单体

采用 TypeScript、Node.js `>=22.12 <26` 的模块化单体仓库，不把 M0—M5 拆成微服务。

原因：

- M0—M5 有紧密且固定的依赖 DAG；
- 一次分析必须固定同一个规则快照；
- 字段权威、去重、全局裁决和安全停止必须原子完成；
- 当前主要复杂度是规则编译和校准，而不是独立扩容；
- 清晰的端口和 Adapter 仍保留未来拆分能力。

领域层不得依赖 HTTP、SQLite、CSV、Excel 或具体历法库。

### 5.2 确定性规则引擎

同一输入、同一规则快照和同一策略配置必须产生相同领域结果。

生产运行时只执行经过版本化治理和自动化测试的类型化 Rule IR。自然语言字段保留为审计资料，但不得在请求期间交给 LLM 或通用文本解释器判断是否命中。

系统可以使用 AI 辅助开发、整理候选映射或生成审阅建议；AI 输出进入生产规则前必须转换为显式 IR，进入版本化 overlay 或新版整合包，并通过契约、语义、安全和回归门禁。当前发布流程不等待逐条人工审批。

### 5.3 双重校验

JSON Schema 负责结构合法性，SemanticValidator 负责跨字段业务不变量。

两者任一失败都不得发布结果。系统错误不能包装成正常的 unknown。

### 5.4 当前 SQLite 与数据边界

当前首版只有两种明确分离的用途：

~~~text
rulesets/<digest>/runtime.sqlite
  规则快照；API 启动时只读打开

calibration.sqlite（可选、显式指定）
  研究案例、冻结预测、反馈、独立复核和变更候选
  不由普通分析 API 或用户界面自动创建
~~~

普通关系分析目前是无会话、无应用数据库写入的请求/响应流程；仓库没有 `app.sqlite`，也不会自动保存出生资料、现实事件或报告。需要持久化用户结果时必须另立契约、隐私模型和迁移方案。校准案例始终与规则快照分域，不得直接写回规则库。

## 7. 有界上下文与职责

### 7.1 Catalog 与治理

负责源文件导入、哈希、ID、列、数量、版本、依赖、迁移映射、IR 编译、快照发布及规则弃用。它不执行用户分析。

### 7.2 出生输入与历法

负责日期、时间、时区、地点、历法、节气交界、四柱生成或校验，以及输入质量和受影响字段。

历法实现必须位于 CalendarPort 后面。具体库、节气数据源、真太阳时策略和边界窗口通过 ADR 冻结。

### 7.3 M0 原局

M0 拥有所有原局静态事实：

~~~text
M02—M05 识别
→ M06 逐对象效应
→ M07—M13 结构
→ M14—M17 候选与功能
→ M18 全局冲突裁决
→ M19 45 项输出
~~~

硬性不变量：

- 关系识别不等于实际效应；
- 原始力量不等于有效力量；
- 十神旺衰不等于喜忌；
- 格局候选不等于格局成立；
- M17 不得绕过 M18；
- M19 的 45 个字段必须全部出现；
- M20、M21 不进入普通推理。

### 7.4 关系画像 M1—M4

- M1：心动和吸引入口；
- M2：关系准入、选择及进入关系前的确认节奏；
- M3：进入关系后的个人表达、照顾、边界和冲突惯性；
- M4：误读、过用、触发、循环、修复卡点和保护候选。

M3 个人惯性不是双方现实事实；M4 结构风险不是已发生伤害。

在 M3.REPAIR、M3.STATE、M3.SYNTH 完成前，受影响结果必须 dependency_pending，并记录三个明确依赖标记。

### 7.5 M5 现实适配

~~~text
BASE
→ PARTNER
→ EXCHANGE
→ BOUND
→ REPAIR
→ RHYTHM
→ GAP
→ SYNTH
~~~

PARTNER、EXCHANGE、BOUND、REPAIR 和 RHYTHM 是不同的现实证据对象，不能压成一个总分。

### 7.6 报告

ReportBuilder 是投影器，不是推理模块。它只能选择已发布字段、组织章节、转换语言、添加观察计划和边界说明。

它不得：

- 补写不存在的事实；
- 重新评分；
- 提高字段状态、置信度或 FG；
- 根据文风生成新结论。

### 7.7 校准

校准案例先冻结预测和版本，再录入匿名现实金标准。校准只能产生 keep、modify_candidate、deprecate_candidate 或 needs_more_evidence。

这是可选研究流程，不是当前发布门禁。研究产生的规则变更只能成为候选；候选必须进入版本化治理、通过回归测试并形成新 Catalog Snapshot，普通分析请求不能直接改写规则。

## 8. Canonical Domain Model

### 8.1 聚合根

| 聚合根 | 作用 | 核心不变量 |
|---|---|---|
| AnalysisRun | 一次完整分析 | 全部模块固定同一快照 |
| RuleCatalogSnapshot | 可发布规则快照 | 不可变、可复现、依赖闭合 |

### 8.2 核心实体和值对象

## 9. 状态和证据必须分离

| 维度 | 回答的问题 | 字段 |
|---|---|---|
| 运行资格 | 源记录是否允许进入普通运行时 | runtimeEligible |
| 编译状态 | 是否已成为可执行 IR | compilationStatus |
| 规则生命周期 | 当前规则是否可采用 | lifecycleStatus |
| 模块状态 | 本次模块是否完整运行 | ModuleStatus |
| 适用状态 | 当前字段是否适用于本次模式 | ApplicabilityStatus |
| 字段状态 | 当前字段结论的性质 | ResultStatus |
| 字段置信 | 结论可靠程度 | ConfidenceLevel |
| 证据深度 | 哪类证据达到多深 | EvidenceDepth |
| 现实门 | 某一 RG 是否通过 | RealityGateStatus |
| 安全状态 | 是否允许继续普通分析 | SafetyStatus |
| FG | 证据允许的发布上限 | FitGrade |
| AF | 关系当前适配状态 | FinalFitState |
| 报告状态 | 报告能否发布 | ReportStatus |

语义约束：

- unknown 是未知，不是负面证据；
- not_assessed 是未评估，不是评估失败；
- not_applicable 属于内部 ApplicabilityStatus，不是模块错误；
- 在 V1.0 外层响应中，不适用字段投影为 status=not_assessed、confidence=not_applicable，并在 conditions 中记录 NOT_APPLICABLE；
- 只有发布新 Schema ID 和迁移表后，才可以把 not_applicable 加入外层 ResultStatus；
- candidate 是结构候选，不是现实发生；
- confidence 不是统计概率；
- base_confidence 是规则元数据，不等于输出置信度；
- FG 是发布上限，不是成功率；
- AF 是当前状态，不是命定结局；
- “规则待验证”和“字段低置信”是不同概念；
- PV、XV、BV、FV、HV、GE 虽都可使用 0—7 深度，但不得互相求和或替换。

同一 sourceId 的基础权重只计一次；同一 eventId 只计一次事件，但可以支持多个字段。

## 10. 出生输入设计

### 10.1 判别联合

~~~ts
type BirthInput =
  | {
      inputMode: "four_pillars_provided";
      subjectId: string;
      fourPillars: {
        year: Pillar;
        month: Pillar;
        day: Pillar;
        hour: Pillar | null;
      };
      birthTimeStatus: "exact" | "approximate" | "unknown";
      timezone?: string;
      dataQuality: DataQuality;
    }
  | {
      inputMode: "civil_datetime";
      subjectId: string;
      localDate: string;
      localTime: string | null;
      timezone: string;
      calendar: "gregorian";
      birthLocation?: GeoPoint;
      birthTimeStatus: "exact" | "approximate" | "unknown";
      dataQuality: DataQuality;
    };

interface Pillar {
  stem: HeavenlyStem;
  branch: EarthlyBranch;
}
~~~

必须校验：

- 天干属于十干、地支属于十二支；
- 每柱属于合法六十甲子；
- 生产分析必须校验年干与月干符合五虎遁、日干与时干符合五鼠遁；
- 日柱必须存在；
- exact 模式必须有精确时刻或时柱；
- unknown 时辰允许 hour=null，但所有时柱依赖字段必须降级；
- 当前只接受 `four_pillars_provided`，并要求 IANA 时区 `Asia/Shanghai`；
- 传统夫妻星策略是显式配置，不与用户现实性别强绑定。

### 10.2 当前输入边界

当前 Schema 只接受 `four_pillars_provided`。`civil_datetime` 会在请求 Schema 层以 HTTP 400 / `E_REQUEST_SCHEMA` 拒绝；Calendar Adapter 完成前不能采用近似算法或隐式换算。

直接提供四柱只表示系统验证干支结构；它不表示系统已经复核出生日期、时区和交节。

analysis_mode=test 可以通过 synthetic_fixture=true 使用专门的合成组合测试识别器，但该输入必须标记为测试资料，不得保存为普通用户分析或生成正式报告。其他模式不得绕过五虎遁和五鼠遁一致性。

## 11. 数据导入和规则编译

### 11.1 Source Package Lock

项目必须创建 data/source-package.lock.json，并使用独立 Schema 校验。它是构建入口，不是自动扫描结果。

lock 必须显式列出：

- 六个集成核心文件；
- M0 V1.9 语义工作簿；
- 29 个 M1—M5 最新原子规则 CSV；
- 每个文件的 path、role、modelVersion、sha256 和 expectedRecordCount；
- M0 标准记录与原生工作簿的 enrichKey、sheet 和 sourceRow 规则；
- 当前启用的版本化 overlay patch；
- 不允许读取的目录前缀。

建议结构：

~~~json
{
  "lock_version": "1.0",
  "integration_version": "1.0",
  "integration_core": [],
  "semantic_sources": {
    "m0": [],
    "m1_m5": []
  },
  "overlays": [],
  "denied_prefixes": [
    "06_历史归档/"
  ]
}
~~~

M0 富化必须通过 globalId、nativeReference、sourceSheet 和 sourceRow 闭合匹配。零匹配、多匹配、行漂移或语义字段不一致都生成 ImportConflict 并阻止构建。

lock Schema 放在 packages/contracts/schemas/source-package-lock.schema.json；DATA-001 必须同时交付 lock、Schema、生成/更新命令和正反 fixture。

### 11.2 V1.0 只读与版本化 Overlay

Integration V1.0 的 161 个文件保持字节级只读。M21 注册缺口、依赖 ID、状态映射和 M5 模板问题不得原地修正。

短期采用项目级版本化 overlay：

~~~text
data/overlays/integration-v1.0-patch-001.json
~~~

每个 patch 必须包含 patchId、目标文件 SHA、目标记录/字段、旧值、新值、裁决依据和治理状态。当前 Schema 只接受 `status: "approved"` 的冻结补丁，并由锁文件、Schema 和回归测试自动验证；这里的状态不是每次构建或分析都要等待的人工审批。overlay 只改变编译视图，原始 native payload 保持不变；其 SHA 必须进入 source-package.lock 和 ruleset digest。

当治理修改稳定后，应发布新的 Integration V1.1，重建文件清单和 SHA，并逐步停用 overlay。开发代码不得直接修改 V1.0 清单来“通过校验”。

### 11.3 编译流水线

~~~text

→ 校验文件清单、字节数和 SHA-256
→ 读取系统版本清单

→ 映射状态、置信、日期和空值

→ 在临时目录构建快照
→ 重开快照并自检

~~~

失败时不得留下可被运行时打开的半成品。

### 11.5 原生值保留

每条导入记录至少保存：

~~~ts
interface SourceReference {
  sourceFile: string;
  sourceSheet?: string;
  sourceRow: number;
  nativeReference: string;
  sourceVersion: string;
  sourceHash: string;
  nativePayload: Record<string, unknown>;
}
~~~

规范化值不能覆盖原值：

- 状态映射同时保存 nativeStatus；
- 置信映射同时保存 nativeConfidence；
- Excel serial 转为 ISO-8601，同时保存原 serial；
- 空字符串不自动变成 false、unknown 或 0；
- 兼容性补空字段不视为错误；
- 未识别的 native 值必须使构建失败。

CF016、CF017、CF018 的映射在 GOV-001 完成前仍是阻塞项。

### 11.6 类型化 Rule IR

禁止提供 evaluate(ruleText) 一类生产接口。

~~~ts
type CompiledRecord =
  | ReferenceDatum
  | PredicateRule
  | RelationRecognitionRule
  | RelationEffectRule
  | GuardrailRule
  | OutputFieldContract;

interface PredicateRule {
  id: RuleId;
  moduleId: ModuleId;
  when: Predicate;
  unless: readonly Predicate[];
  effects: readonly RuleEffect[];
  priority: Priority;
  source: SourceReference;
}
~~~

Predicate 只允许受控 AST 节点，例如 all、any、not、equals、in、exists、relationExists 和 compareEvidence。禁止任意 JavaScript、SQL 和自然语言表达式。

每条源记录必须进入以下一种状态：

~~~text
compiled
reference_only
guardrail
test_only
governance
unsupported_with_reason
~~~

静默丢弃数必须为 0。

### 11.7 编译产物

~~~text

  ruleset-manifest.json
  runtime.sqlite
  schemas/
  coverage.json
  fixtures/m20.jsonl
  governance/m21.jsonl
~~~

ruleset_digest 由权威源内容、overlay、编译器版本、字段权威、语义策略和策略配置共同计算，不包含构建时间。

manifest 至少记录：

- Integration 和 M0—M5 版本；
- Schema ID；
- 编译器版本；

- 字段权威摘要 fieldAuthorityDigest；
- 安全、RG、FG/AF 等语义策略摘要 semanticPolicyDigest；
- 夫妻星、历法和运行模式等策略摘要 strategyConfigDigest；

## 12. 运行时加载

运行时只打开已编译快照，禁止 CSV/XLSX 回退。

~~~text

→ 校验 manifest 与 Schema ID
→ 校验版本、数量和编译覆盖阈值
→ 校验活动依赖 DAG
~~~

每个请求固定一个 ruleset_digest，执行过程中不得切换。首版不实现热加载；规则更新后重启服务。

诊断端点必须区分：

~~~jsonc
{
  "status": "ready",
  "catalog": {
    "rulesetDigest": "<64-hex>",
    "loadedRecords": 10918,
    "compiledRecords": 10873,
    "activeModules": ["M0.M02", "M0.M03", "...", "M5.SYNTH"] // 文档缩写；实际返回完整数组
  }

~~~

`loadedRecords` 不得冒充 `compiledRecords`。当前差额包含具有明确非编译处置的记录，不是静默丢弃；`silentDrops` 必须保持 0。

## 13. Schema、语义验证和错误模型

### 13.1 验证顺序

~~~text
请求 Schema
→ 领域输入校验
→ 分析执行
→ 领域 SemanticValidator
→ ReportBuilder
→ DTO Adapter
→ 端点响应 Schema
→ 发布
~~~

### 13.2 当前契约冲突的实施裁决

| 冲突 | 实施裁决 |
|---|---|
| 统一 Schema 要求 M0—M5 全部存在 | 每个端点建立独立响应 Schema；完整关系接口才使用全量 Schema |
| 接口文档含 module_id/warnings/errors，Schema 禁止 | 内部使用富 ModuleRun；外部统一投影为 issues |
| not_applicable 位置冲突 | 内部建立 ApplicabilityStatus；V1.0 外层投影为 not_assessed＋confidence=not_applicable；新状态留待 V1.1 |
| ResultItem.value 允许任意类型 | 为每个稳定输出字段生成值类型 Schema |
| birth_time_status 与时刻没有条件约束 | 使用判别联合及 if/then |
| RG 数组不能保证八个唯一代码 | SemanticValidator 校验集合恰为 RG01—RG08 |
| M4/M5 模块 Schema 与统一 Schema 不同构 | 保留模块原生 Schema，通过显式 Adapter 转公共投影 |
| Schema 未表达安全、FG 和 M3 依赖 | 由版本化语义策略执行 |
| 输出槽位路径 modules.m* 与根级 m* 冲突 | 新端点契约统一根级路径，旧路径通过迁移表记录 |

现有 V1.0 Schema 和源文件保持只读；修订以新的契约版本和迁移说明发布。

### 13.3 语义校验清单

发布前至少校验：

1. M19 恰有 45 个字段；
2. not_assessed 使用 value=null，不伪造规则命中；
3. applicability=not_applicable 时，V1.0 投影符合 not_assessed 兼容规则；
4. unknown 使用 value=null、confidence=unknown，并记录原因；
5. 每个 ruleId 属于当前快照和正确模块；
6. sourceId/eventId 存在且唯一；
7. 普通结果不引用 M20/M21；
8. complete 模块的必需依赖均已完成；
9. M3 不可用或本次输入依赖缺失时传播 dependency flags 并降级；
10. 单盘模式不输出具体对象或 FG3/FG4；
11. RG01—RG08 各出现一次；
12. RG01 失败得到 stop、safety_stop、FG0、AF09；
13. 核心 RG 未知或失败时 FG 不高于 FG2；
14. 安全停止后普通适配报告段为空或 stopped；
15. boundaries 的硬边界全部为 true；
16. 结构或语义任一失败时不发布结果。

~~~ts
interface DomainIssue {
  code: string;
  severity: "error" | "warning";
  stage: "request" | "birth_input" | "ruleset" | "module" | "publication";
  message: string;
  jsonPointer?: string;
~~~

| 情形 | HTTP | 处理 |

## 17. 当前持久化模型

普通分析 API 不持久化用户输入或结果。当前落盘边界只有：

~~~text
rulesets/<digest>/
  runtime.sqlite              # 10,918 条运行时记录，只读
  ruleset-manifest.json       # digest、版本、数量和覆盖
  coverage.json
  fixtures/m20.jsonl
  governance/m21.jsonl

calibration.sqlite            # 仅在显式研究流程中创建；不接入普通 API/UI
~~~

每次分析响应都携带 requestId、generatedAt、rulesetDigest、ruleTrace 和 sourceIds，界面可展示摘要并提供完整 JSON 导出入口，但服务器不会自动保存该响应。本次浏览器验收没有把下载文件落盘事件计为已验证能力。

如果以后增加 `app.sqlite` 或其他用户数据存储，必须先定义同意、最小化、保留/删除、迁移、访问审计和身份边界；该目标模型不是当前已实现能力。CalibrationCase 仍只能生成变更候选，不能直接修改 Catalog Snapshot。

## 18. 隐私与安全

- 当前 API 不写入请求正文、出生资料或现实事件日志，只输出启动诊断；
- 未来若增加请求日志，只允许使用 requestId 和不可逆的匿名 subjectId；
- 事件正文与结构化标签分离，访问需审计；
- 校准案例必须取得同意并匿名化；
- 导出数据不得包含可逆身份映射；
- sourceId/eventId 去重在匿名化后仍须稳定；
- 报告中的安全停止保留必要说明，但不暴露无关敏感细节；
- 运行时不执行来自 CSV、用户输入或数据库的代码；
- IR AST 不允许任意脚本、SQL 和网络调用；
- 规则快照使用内容哈希和只读打开方式。
